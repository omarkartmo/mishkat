# MISHKAT SETUP BUILD WORKFLOW

Use this workflow whenever I ask you to build the MISHKAT installer (`MISHKAT-Setup.exe`) for testing or delivery.

## OBJECTIVE

Build the real production Tauri installer from the current source code.

The final artifact must be a Windows installer:

`MISHKAT-Setup.exe`

Do NOT create a GitHub Release in this workflow.

Do NOT create or push a Git tag.

Do NOT modify the update system.

Do NOT modify application functionality unless explicitly requested.

---

## PHASE 1 — PRE-BUILD SAFETY

1. Run:

```powershell
git status
```

2. Inspect the current branch and working tree.

3. Do not discard, reset, stash, or overwrite existing user changes.

4. Verify the application version from `package.json`.

5. Inspect the actual Tauri configuration and determine:

   * Tauri version
   * application identifier
   * installer configuration
   * bundle targets
   * output directory

6. Verify that the project is currently intended to build as the final Tauri desktop application.

7. Confirm that Electron is NOT being used as a parallel production runtime.

---

## PHASE 2 — DEPENDENCY VERIFICATION

Verify that all required dependencies are available.

Use the project's existing lockfile.

Prefer:

```powershell
npm ci
```

Do NOT replace `npm ci` with `npm install` unless there is a documented reason.

Verify:

* Node.js
* npm
* Rust
* Cargo
* Tauri CLI
* frontend dependencies
* required build tools

If a required dependency is missing, report the exact missing dependency and stop rather than silently changing the environment.

---

## PHASE 3 — VALIDATION BEFORE BUILD

Run the project's appropriate checks:

```powershell
npx tsc --noEmit
```

Run the existing test suite:

```powershell
npm test
```

if configured.

Run lint if configured.

Do not invent tests that do not exist.

If a check fails:

1. identify the actual error;
2. determine whether it is related to the requested build;
3. fix only if explicitly authorized to fix build-blocking issues;
4. rerun the failed verification.

Do not declare the installer ready merely because TypeScript compiles.

---

## PHASE 4 — PRODUCTION BUILD

Use the project's existing production Tauri build command.

First inspect `package.json` and the Tauri configuration to determine the canonical command.

Prefer the project's existing command rather than inventing a new build process.

The expected operation is equivalent to:

```powershell
npm run tauri build
```

or the project's configured Tauri production-build command.

Build the Windows installer in production mode.

Do not use development mode.

Do not use:

```powershell
npm run dev
```

as evidence that the installer works.

---

## PHASE 5 — LOCATE THE REAL INSTALLER

After the build completes:

1. Search the Tauri bundle/output directories.
2. Locate the actual Windows installer.
3. Confirm that the expected installer exists.

Expected artifact:

```text
MISHKAT-Setup.exe
```

If the project intentionally generates another filename, inspect the Tauri configuration and report the actual generated filename instead of renaming it blindly.

---

## PHASE 6 — ARTIFACT VERIFICATION

Verify the generated installer:

* exists;
* is a Windows executable;
* has a non-zero file size;
* was generated by the current build;
* corresponds to the current application version.

Calculate its SHA-256:

```powershell
Get-FileHash "<installer-path>" -Algorithm SHA256
```

Record:

* installer path;
* file size;
* application version;
* SHA-256.

Do NOT modify the installer after calculating its checksum.

---

## PHASE 7 — REAL INSTALLATION TEST

Install the generated installer on the Windows test machine.

This is mandatory for a release candidate.

Verify:

1. Installation completes successfully.
2. MISHKAT launches from the installed shortcut.
3. It launches as the intended Tauri desktop application.
4. It does NOT unexpectedly open the application in Chrome.
5. The application connects to its local server/runtime correctly.
6. Existing data is preserved when upgrading an existing installation.
7. The application version displayed by the application matches `package.json`.

Do not confuse:

* development mode;
* browser preview;
* local source execution;
* installed production application.

The objective is to test the actual installed `.exe`.

---

## PHASE 8 — CRITICAL REGRESSION CHECK

Before declaring the installer successful, test the critical functionality affected by the current changes.

At minimum, verify the relevant existing functionality that must not regress.

For update-related builds, pay particular attention to:

* database integrity;
* backup;
* restore;
* sample/demo data restoration;
* book import;
* PDF/book metadata extraction;
* Arabic text rendering;
* reader page synchronization;
* internet policy/proxy;
* student/server modes;
* Admin settings;
* support/error reporting.

Do not assume previously working functionality still works after a build.

---

## PHASE 9 — FINAL REPORT

Return a concise report containing:

### Build

* Version
* Build command
* Build result

### Installer

* Exact installer path
* File size
* SHA-256

### Installation test

* Installed successfully: PASS/FAIL
* Launches as desktop app: PASS/FAIL
* Opens browser unexpectedly: PASS/FAIL

### Regression tests

List only tests actually performed and their real result.

### Final status

Use exactly one of:

`BUILD READY FOR TESTING`

or

`BUILD FAILED`

or

`BUILD READY FOR RELEASE`

Never claim `READY FOR RELEASE` unless the real installed production artifact has been tested successfully.

---

## HARD RULES

* Never create a GitHub Release from this workflow.
* Never create or push a Git tag.
* Never use a PAT.
* Never expose secrets.
* Never overwrite `.env`.
* Never reset or discard user changes.
* Never modify working application code just to make the build appear successful.
* Never call a development/browser run an installer test.
* Never claim success without evidence.
* If the installer build succeeds but the installed application fails, report BUILD FAILED.
