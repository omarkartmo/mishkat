# معمارية النسخ الاحتياطي والاسترجاع وتصدير البيانات في نظام مشكاة
# MISHKAT Backup, Restore & Data Export Architecture Guide

توثيق تقني ومعماري شامل لمنظومة النسخ الاحتياطي المشفر (Disaster Recovery Backup)، الاسترجاع الذري (Atomic ACID Restore)، وتصدير البيانات المفتوحة (Institutional Data Export) المصممة للعمل محلياً في نظام «مشكاة» (On-Premises / Air-Gapped) دون أي اعتماد على خدمات سحابية أو طرف ثالث.

---

## 1. مسارات التخزين المحلي (Local Storage Locations)

يعمل النظام بالكامل ضمن مجلد التخزين المركزي `LibraryData/` دون تداخل مع الشيفرة المصدرية:
* **مجلد النسخ الاحتياطية:** `LibraryData/backups/`
  يحتوي على كافة ملفات النسخ الاحتياطية المشفرة بصيغة JSON المغلفة (`mishkat_backup_*.json`) وملفات الأمان التلقائية السابقة للاسترجاع (`mishkat_pre_restore_*.json`).
* **مجلد المفاتيح والأسرار المحلية:** `LibraryData/secrets/`
  يحتوي على مفتاح التشفير الرئيسي المشتق عشوائياً `backup.key` بصلاحيات نظام تشغيل مشددة (0o600).
* **مستودع الكتب الرقمية والوسائط:** `LibraryData/books/`
  يحتوي على الملفات الثنائية للكتب الرقمية (`LibraryData/books/digital/`) وصور الأغلفة (`LibraryData/books/covers/`) والملفات المؤقتة وقائمة الانتظار (`LibraryData/books/incoming/`).

---

## 2. خوارزمية التشفير والمصادقة (AES-256-GCM AEAD)

تعتمد منظومة النسخ الاحتياطي خوارزمية **AES-256-GCM** (Advanced Encryption Standard in Galois/Counter Mode) عبر مكتبة `crypto` المدمجة في بيئة Node.js (OpenSSL القياسي):
* **طول المفتاح:** 256 بت (32 بايت).
* **متجه التهيئة (IV):** 96 بت (12 بايت) يتم توليده عشوائياً بشكل آمن لكل عملية نسخ احتياطي باستخدام CSPRNG (`crypto.randomBytes`).
* **توقيع المصادقة والسلامة (Auth Tag):** 128 بت (16 بايت) يضمن التحقق الفوري من أصالة البيانات وعدم التلاعب بها أو تلفها قبل فك التشفير.
* **فحص التجزئة المزدوج:** بالإضافة إلى `authTag`، يتم حساب تجزئة **SHA-256** للنص الأصلي وحفظها في الترويسة للتحقق الإضافي بعد فك التشفير.

### هيكل الغلاف المشفر (Encrypted Envelope)
```json
{
  "format": "mishkat_encrypted_backup",
  "version": "2.0.0",
  "algorithm": "aes-256-gcm",
  "kdf": "pbkdf2-sha256",
  "salt": "<32 hex chars>",
  "iv": "<24 hex chars>",
  "authTag": "<32 hex chars>",
  "sha256": "<64 hex chars>",
  "meta": {
    "exportedAt": "2026-09-15T19:00:00.000Z",
    "exportedBy": "مدير النظام",
    "version": "2.0.0",
    "application": "MISHKAT",
    "type": "manual | pre_restore",
    "tablesCount": 16
  },
  "ciphertext": "<base64 encoded encrypted payload>"
}
```

## 3. إدارة مفاتيح التشفير للبيئة المحلية (Key Management)

نظراً لعمل نظام مشكاة في بيئة محلية مستقلة دون اتصال بالإنترنت، تتم إدارة المفاتيح وفق المستويات التالية:
1. **متغير البيئة `BACKUP_ENCRYPTION_KEY`:** إذا تم توفيره بطول 16 حرفاً على الأقل في ملف `.env` أو متغيرات النظام.
2. **المفتاح المحلي المحمي:** قراءة المفتاح من `LibraryData/secrets/backup.key`، وفي حال عدم وجوده يتم توليد مفتاح عشوائي آمن بطول 256 بت وحفظه في الملف.
3. **اشتقاق المفتاح (KDF):** يتم استخدام **PBKDF2-HMAC-SHA256** مع 100,000 تكرار (Iterations) و salt عشوائي 16 بايت لكل نسخة لتوليد مفتاح التشفير 32 بايت، مما يحمي النسخ ضد هجمات القواميس وجداول Rainbow Tables.

## 4. الفصل المعماري: النسخ الاحتياطي مقابل تصدير البيانات

| الخاصية | النسخ الاحتياطي (Database Backup) | تصدير بيانات المؤسسة (Data Export) |
| :--- | :--- | :--- |
| **الهدف الأساسي** | استعادة النظام عند الكوارث (Disaster Recovery). | ترحيل البيانات لنظام آخر أو التحليل والمراجعة الخارجية. |
| **التشفير** | مشفر بالكامل بـ AES-256-GCM مع Auth Tag. | غير مشفر (JSON قياسي مفتوح ومقروء). |
| **البيانات الحساسة والأسرار** | يتضمن كافة الجداول والهاشات لضمان عودة النظام للعمل دون فقدان صلاحيات المستخدمين. | **محظور ومستبعد تماماً:** لا يشمل كلمات المرور، أسئلة الأمان، أو رموز الجلسات. |
| **التوافق** | مخصص لنظام مشكاة حصراً للاسترجاع المتطابق. | صيغة عالمية مفتوحة تقبل الاستيراد في أي قاعدة بيانات أو جداول Excel. |
| **نقطة النهاية** | `POST /api/v1/backups/create` | `POST /api/v1/system/export-data` |

---

## 5. تعقيم الأسرار في تصدير البيانات (Sanitization)

عند طلب `POST /api/v1/system/export-data`:
* **جدول المستخدمين (`users`):** يتم جلب كافة الحقول الأكاديمية والشخصية مع **استبعاد صريح** للحقول:
  - `password_hash`
  - `security_question`
  - `security_answer_hash`
  - `token_version`
* **جدول الإعدادات (`system_settings`):** استبعاد أي إعداد يحتوي اسمه على كلمات مثل `secret` أو `key` أو `password` أو `token`.

---

## 6. الاسترجاع الذري بالكامل (Atomic ACID Transaction)

عملية الاسترجاع تتم داخل معاملة ذرية واحدة عبر بروتوكول ACID:
```sql
BEGIN;
  -- 1. التفريغ المتسلسل لكافة الجداول الـ 16
  TRUNCATE TABLE
    staging_queue,
    notifications,
    student_notes,
    book_summaries,
    physical_bookmarks,
    reading_progress,
    student_favorites,
    loans,
    loan_requests,
    pending_submissions,
    whitelisted_portals,
    physical_copies,
    books,
    categories,
    users,
    system_settings
  CASCADE;

  -- 2. إدخال السجلات جدولاً تلو الآخر وفق مصفوفة التبعيات
  -- INSERT INTO ...

  -- 3. الفحص الأمني بعد الإدخال: التحقق من وجود حساب مدير نشط (Admin Guard)
  -- SELECT id FROM users WHERE role_id = 'admin' AND ...
COMMIT;
```
في حال حدوث أي خطأ برمجي، تعارض قيود، أو انقطاع أثناء الاسترجاع، يقوم الخادم بتنفيذ `ROLLBACK` فوري يعيد قاعدة البيانات بدقة إلى حالتها الأصلية قبل البدء.

## 7. نسخة الأمان التلقائية المسبقة (Pre-Restore Safety Backup)

قبل فتح أي معاملة استرجاع أو لمس أي جدول:
1. يقوم الخادم آلياً بتوليد نسخة احتياطية مشفرة للحالة الراهنة باسم يبدأ بـ `mishkat_pre_restore_<timestamp>.json`.
2. في حال فشل إنشاء نسخة الأمان لأي سبب (مثل امتلاء القرص)، يتم إيقاف عملية الاسترجاع فوراً برمز خطأ `SAFETY_BACKUP_FAILED` لحماية بيانات المؤسسة.

---

## 8. معالجة وتفريغ جدول `staging_queue`

تم إصلاح استثناء `staging_queue`؛ حيث تم تضمينه صراحة في:
* أمر `TRUNCATE TABLE staging_queue, ... CASCADE;` لمنع بقاء أي عناصر قديمة عالقة من فحص مجلد الوارد.
* دالة التحقق `validateBackupPayload` للتحقق من عدم تكرار المعرفات وسلامة الحقول الأساسية.
* مصفوفة ترتيب الإدخال `BACKUP_TABLES_ORDER`.

---

## 9. التوافقية العكسية (Backward Compatibility)

يدعم النظام قراءة واسترجاع النسخ السابقة غير المشفرة الإصدار v1.0.0:
* عند استلام ملف نسخة، يتم فحصه تلقائياً؛ إذا كان غلافاً مشفراً v2.0.0 يتم فك تشفيره والتحقق من `authTag`.
* إذا كان ملفاً قديماً v1.0.0 مفتوحاً، يتم تحليله وقبوله مع تسجيل تحذير أمني في سجل التدقيق الرقابي (`audit_logs`) يوضح أن الاسترجاع تم من نسخة غير مشفرة.

---

## 10. حفظ الكتب الرقمية والأغلفة (Media & Cold Storage)

النسخة الاحتياطية المشفرة وتصدير البيانات يتناولان قاعدة البيانات المركزية ومسارات وهاشات الملفات (Metadata & Content Hash).
أما الملفات الثنائية نفسها (PDF, EPUB, JPG, PNG) فهي مخزنة كملفات نظام في:
* `LibraryData/books/digital/`
* `LibraryData/books/covers/`
* `LibraryData/books/incoming/`

**إجراء الحفظ الخارجي الموصى به للمؤسسة:**
يوصى مدير النظام بأخذ نسخة دورية من كامل مجلد `LibraryData/` إلى قرص صلب خارجي مشفر أو وحدة تخزين منفصلة (Air-gapped Storage) لضمان اكتمال الحفظ الرقمي والبياني.

---

## 11. سجل التدقيق والرقابة (Audit Trail)

تسجل كافة العمليات في جدول `audit_logs`:
* `CREATE_BACKUP`: مع اسم الملف، عدد الجداول، ونوع التشفير.
* `RESTORE_DATABASE`: مع اسم ملف النسخة، واسم نسخة الأمان المنشأة، وعدد السجلات المسترجعة، وحالة التشفير.
* `EXPORT_INSTITUTIONAL_DATA`: مع عدد السجلات المصدرة وإصدار التصدير ومعرف المدير المنفذ.

---

## 12. ضوابط الأمان والصلاحيات (RBAC & Path Traversal)

* كافة المسارات مقيدة بالمدير حصراً (`requireRole('admin')`).
* تتطلب العمليات تأكيداً صريحاً في جسم الطلب `{ confirm: true }`.
* فحص مسارات الملفات (`path.basename`, `path.relative`) لمنع أي هجمات لتجاوز المسار (Path Traversal Protection).
